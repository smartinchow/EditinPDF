# EditinPDF M2 + M3 (organize, save, annotate, forms) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the shipped read-only viewer into a mobile PDF editor: pages are reorganized (rotate, delete, reorder, insert blank, merge, extract), marked up (highlight, underline, strikeout, ink, text box, note, shapes, arrow), forms are filled, every change is undoable, and the file autosaves in place without damaging the original bytes.

**Architecture:** The bridge `editinpdf-core` gains a curated `Edit` enum (view-space geometry, 0-based pages) that it converts to upstream `pdfcraft_engine::Edit` with `pdfcraft_render::PageInfo::view_to_user`, plus undo/redo, a revision counter that invalidates every cache, `save` (incremental by default), `extract_pages`, `annotations` and `form_fields`. The app switches to an editing `DocumentGroup`; `PDFFileDocument`'s snapshot is the engine document and the bytes are written by `save(.incremental)`. `DocumentModel` runs every edit through one serial queue off the main actor, registers it with the scene's `UndoManager`, and republishes pages/annotations/fields per revision; the page view, thumbnails, organize grid, tool overlays and form overlays all key off that revision.

**Tech Stack:** Rust 1.99 (edition 2024), UniFFI 0.32 (proc-macros), PdfCraft v0.7.1 (submodule, never edited), Swift 6 (strict concurrency) / SwiftUI / UIKit / PencilKit, iOS 17+, XcodeGen, XCTest.

**Spec:** `docs/superpowers/specs/2026-10-15-editinpdf-ios-design.md` (this plan covers spec milestones M2 and M3; §4.2–4.3 bridge API, §5 app design; amended by "M2–M3 scope update (2026-10-18)" at the end of the spec, committed with this plan).

## Review Focus

1. **Autosave must never damage the file.** Saving an unedited document returns the original bytes unchanged; saving an edited one returns the original bytes followed by an appended update; a document that is locked or failed to open is never written. Tests: Task 1 (`unedited_save_is_the_original_bytes`, `edited_incremental_save_appends_to_the_original`), Task 8 (`testSnapshotOfLockedOrFailedDocumentThrows`).
2. **Autosave racing an edit writes a half-applied state.** A save that runs while edits apply on another thread yields either the state before or after each edit, never between; a multi-part change (multi-delete, eraser stroke) is one `apply_all`, all or nothing. Tests: Task 1 (`saves_racing_edits_always_reopen_whole`, `a_failing_batch_changes_nothing`).
3. **Undo after a page delete leaves stale page or annotation indices.** Undoing/redoing re-reads pages, clamps the current page, clears text selection, the selected annotation and the organize selection; an edit computed against an older revision is refused by the bridge (`Stale`) instead of hitting the wrong page. Tests: Task 1 (`an_edit_for_an_old_revision_is_refused`), Task 9 (`testUndoOfDeleteOnLastPageKeepsCurrentPageValid`), Task 17 (`testEraserDeletesHighestIndexFirst`).
4. **Annotations land in the wrong place on rotated pages** (`/Rotate 90/180/270`, non-zero crop origin). What the user drew in view space comes back from `annotations()` at the same view-space place. Tests: Task 4 (`view_user_round_trip_every_rotation`, `highlight_on_rotated_page_comes_back_where_drawn`), Task 5 (`ink_on_rotated_page_comes_back_where_drawn`), Task 15 (`testCanvasPointsBecomePagePointsAtAnyZoom`).
5. **An encrypted document is re-saved without its password, or an edit fails silently on a restricted one.** Saves of an edited encrypted file still need the same password; permission-restricted files disable the matching tools and a refused edit shows its reason. Tests: Task 1 (`encrypted_document_stays_encrypted_after_edit_and_save`), Task 3 (`inserting_into_an_encrypted_document_keeps_it_encrypted`), Task 9 (`testRefusedEditShowsReasonAndLeavesUndoStackAlone`).

  Undo protocol (the decision that keeps the two stacks aligned): `perform` registers its UndoManager entry **synchronously, before** queuing the engine call, with an `EditToken` (`final class`, `var applied = false`). The queued engine call sets `token.applied = true` on success; on failure it sets `failure` and leaves the entry, whose handler is then a no-op. The undo handler registers the redo entry (same token, same action name) synchronously and queues `document.undo()` only if `token.applied`; redo mirrors it. A failing engine undo/redo sets `failure` and calls `undoManager.removeAllActions(withTarget: self)`. Because handler and edit share the one queue, an undo tapped while an edit is still running undoes that edit, never an older one.
